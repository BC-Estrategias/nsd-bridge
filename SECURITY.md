# Security

## Threat model
The console and the computer are on the same LAN. The agent defends against **other devices on that LAN** and against an **assistant that only has the MCP tools**:
- **the CLI and the MCP server (the TCP port)**: nobody can read or write the SD card without having been paired by a person at the console (the person presses A on the console after comparing a 6-digit number shown on both screens: an X25519 key agreement with a commitment, so the key never crosses the network and a man in the middle cannot fake a match; or the older 80-bit one-time code; then per-frame HMAC-SHA-256 with counters, so tampering and replay close the connection). Five refused requests close the pairing window;
- nothing on the network can change the access mode, the opened folders or the pairings — those are changed with the console's buttons only;
- protected system zones are never writable, and deletes only move items to a trash folder; permanent deletion (`FS_PURGE`) works only on what is already inside a trash, needs DEVELOPMENT mode, and is not available through the MCP server.

The **web page** is different since v1.7.1: it needs **no pairing by default**. Any device on the same Wi-Fi that opens the console's address while the app is open can browse (read) the folders you opened, with no password; this is a deliberate trade-off for a home console, so use it only on networks you trust. It is still limited by the console's own controls, which nothing on the network can change: the app always starts READ-ONLY, writing needs you to press X and to have opened a folder for writing, and the protected zones stay unwritable. A page connection cannot see or forget the list of paired computers. Creating a file named `require-web-pairing` in the config folder (`/3ds/nintendo-dev-agent/config` or `/nsd-bridge/config`) makes the page pair like any other client again (the older behaviour: number comparison, then sealed frames). The page's other protections are unchanged: the console rejects requests whose `Host` is not its own address (DNS rebinding) and WebSocket upgrades whose `Origin` is not the page itself (so a malicious website cannot drive it through your browser), accepts only `GET`/`HEAD` with no body, serves a strict Content-Security-Policy, and caps frame and header sizes. When the page is paired, the key is kept in the browser's storage (untick "Remember" on shared computers, or use *Forget this browser*).

The **self-update** of the 3DS agent (v1.7.0+) is the only thing in this project that makes outgoing connections from the console. A few seconds after the network is up, it asks `api.github.com` for this repository's latest release (a file named `no-update-check` in `/3ds/nintendo-dev-agent/config` turns that automatic check off). It never installs anything on its own: a person presses the *Updates* entry on the console. It accepts only HTTPS, verifies the server certificate against an embedded Mozilla CA bundle, downloads only files under this repository's own `releases/download/` path, and checks the SHA-256 and size that GitHub reports for the file before installing (the CIA is installed over the existing title and must carry this app's title ID). The download is staged in the protected `config` folder, which no protocol command can write. Limit: the hash comes from the same GitHub account that publishes the file, so it protects against a corrupted or swapped download, **not** against that account being compromised.

The **web page asks `api.github.com` for the latest release number** from your browser (not from the console) to show an "update available" banner; it sends nothing about the console and can be turned off in Settings. The console's content-security policy allows only that one extra address. `ndev update` (DSi) downloads only from this repository's release path and refuses a file whose size or SHA-256 differs from what GitHub reports; as with the 3DS updater, that protects against a corrupted or swapped download, not against a compromised publishing account.

The **3DS installer** (v1.8.0) installs software, so every path to it ends at a confirmation on the console itself: a request from the page, `ndev` or a QR code is only taken while the *Receive from the browser* / scanner screen is open and nothing is downloaded or installed until the owner presses A on a screen that shows the origin and the title. An unpaired page can send such a request (that is the gate), but it cannot make the console install anything by itself. The install checks the CIA size against its header and, when given a SHA-256, the hash before the install is committed; HTTPS certificates are verified. These checks protect against corruption and tampering in transit, not against a malicious CIA you choose to confirm: **a CIA is arbitrary code**. Titles destined for system memory are flagged in red, firmware titles are refused.

Not protected against: someone who can read your computer's `~/.config/nintendo-dev/keys.json` (owner-only file, but any program running as you can read it, including an assistant with shell access); an eavesdropper on your LAN reading file contents (the channel is authenticated, **not encrypted**); physical access to the console or its SD card.

## Reporting a vulnerability
Please do not open a public issue. Contact the maintainers privately (BC Labs, via the repository's owner on GitHub) with the affected version and steps to reproduce. We aim to acknowledge within a few days.

## Verification done
The protocol core is tested by an independent Python reference (vectors), sanitizers (ASan/UBSan), mutation testing of the security-critical checks, and hardware tests on a New 3DS. This is not a formal audit.
